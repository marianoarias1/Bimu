# Revisión inicial de seguridad — 2026-11-03

## Base y límites

Base: Bimu **0.55.9**, `main` **dba4d47a6b529a02bb1a074838ac86f63cfe7e4b**. Correcciones propuestas en **0.55.10**, sujetas a CI y prueba instalada. Revisión de código fuente y configuración; no es pentest independiente ni certificación OWASP/CIS/NIST. No se ejecutaron ataques sobre equipos de terceros o la PC del usuario. No se evaluaron binarios publicados con desensamblado, estado real de Defender/EDR, certificado Store ni cambios administrativos de cuenta.

Modelo: atacante no vinculado en la misma red; peer vinculado malicioso/comprometido; respuesta de proveedor HTTP anómala; configuración local corrupta; dependencias/pipeline comprometidos. Un atacante con ejecución bajo la misma cuenta Windows ya puede leer/modificar datos del usuario y usar DPAPI: no se promete aislarlo dentro de Bimu.

## Hallazgos y correcciones

| ID / prioridad | Evidencia y precondición | Impacto delimitado | Tratamiento |
|---|---|---|---|
| H-01 / media | `pairing_transport.rs`: `read_exact` con timeout de socket reiniciado en lecturas sucesivas; el plazo del código se comprueba fuera del handshake. Requiere conexión LAN al listener. | Un peer sin autenticar que gotea bytes puede prolongar la ocupación del worker. No demuestra descifrado, acceso a archivos ni RCE. | Plazo absoluto de 10 s para PAKE + Noise/reconexión; lecturas/escrituras parciales verifican tiempo restante. Se restaura el timeout normal al establecer canal. Transferencias establecidas sin cambio de timeout. Regresiones de goteo y plazo vencido. |
| H-02 / media | `weather.rs` usa `response.bytes()` antes del límite; `updates_check` deserializa JSON sin límite del cuerpo. Requiere respuesta sobredimensionada del servicio confiado/comprometido. | Consumo de memoria superior al límite pretendido. No es SSRF arbitrario: destinos son constantes/validados. | Lector HTTP incremental acotado a 1 MB, con y sin Content-Length; cliente de clima solo HTTPS y timeout de conexión. Pruebas de límite exacto, chunked, cabecera enorme y JSON inválido. |
| H-03 / baja | `trusted_pairing.rs`, inicio y bandeja usan `fs::read` antes de validar tamaño; migración/perfiles hacen precheck de metadatos pero no acotan el read. Requiere configuración corrupta o modificable localmente. | Presión de memoria/indisponibilidad local; no se atribuye escalada de privilegios. | Lectura real con `take(max+1)`, conservando formatos, rutas y límites. Bandeja 1 MB, vinculación 4 KB, inicio 1 KB, perfiles 8 MB. Pruebas con fuente creciente y límites exactos. |
| H-04 / baja | Bandeja/credencial se escriben directamente; configuraciones comparten nombre temporal predecible. | Pérdida de configuración ante interrupción; manipulación local del temporal dentro de permisos del usuario. No prueba escritura fuera de privilegios de la cuenta. | Archivo temporal exclusivo (`create_new`), nombre único, sync y reemplazo, limpieza ante error. Bandeja/inicio/vinculación reutilizan escritor atómico. Prueba conserva datos y no toca un temporal preexistente. |
| H-05 / media | Filtro de nombres de transferencias contempla COM1–9/LPT1–9 pero omite los dígitos ¹²³ reconocidos por Windows; faltan aliases de consola. Requiere payload de peer autenticado. | El nombre supera la validación previa y puede ser interpretado como dispositivo o fallar al escribir. No se afirma ejecución de código. | Rechazo de COM/LPT con superíndices y CONIN$/CONOUT$ antes de crear destino. Prueba usa raíz/entrada coincidentes para no pasar por rechazo incidental de ruta. |
| H-06 / media (proceso) | No había workflow periódico de dependencias Rust ni guard de configuración; `dtolnay/rust-toolchain@stable` es una referencia móvil. | Cambios de dependencias/actions pueden entrar sin evaluación de avisos nuevos. | Security baseline, artefactos npm/RustSec, Dependabot y pin de la acción por SHA. El compilador stable aún se actualiza: decisión explícita, no build hermético. |
| H-07 / media (administración, pendiente) | Ruleset público `Proteger main` activo: bloquea borrado/force push y exige PR, pero no contiene `required_status_checks`; aprobaciones requeridas = 0. | Una PR puede fusionarse sin checks obligatorios según esa regla consultada. | Propietario: requerir `verify`, `policy-and-npm` y `rust-advisories` usando los nombres reales disponibles después del build. Considerar revisión independiente/resolución de conversaciones. No se modificó la regla administrativa. El workflow de publicación del EXE ahora depende además de Security baseline, de modo que un fallo bloquea esa publicación automática. |

CSP: defensa adicional `object-src`, `base-uri`, `form-action`, `frame-ancestors` en `'none'`. Se mantienen scripts locales e IPC existente. No se amplían capabilities ni se quita `unsafe-inline` de estilos porque la UI usa estilos dinámicos; no se confunde con `unsafe-eval`/scripts inline.

## Controles existentes revisados

- SPAKE2 con confirmación HMAC ligada al rol; derivación PSK y canal Noise autenticado. No se envía contenido de aplicación antes de autenticar. Código generado con OsRng, seis dígitos, 120 s y un intento por código.
- Credencial aleatoria persistente de 32 bytes protegida con DPAPI de usuario. La dirección o anuncio UDP no sustituye la autenticación; los tags de reconexión no contienen la clave.
- Catálogo remoto sin rutas absolutas; respuesta de archivo solicitada debe coincidir en ID, token y nombre. Validaciones de rutas relativas, duplicados, raíces, profundidad/cantidad, límites por selección y rechazo de reparse points. Extracción en directorio nuevo, archivos `create_new` y limpieza ante fallo.
- Historial limitado a 30 entradas / 48 MB de contenido, texto 1 MB, imagen 12 MB; respeta indicadores Windows de exclusión/historial/compartición. Texto e imágenes no se persisten como historial en disco.
- Atajos: IDs de aplicaciones registradas, .exe/.lnk/ShellApp controlados, argumentos separados, perfiles validados y URL http(s); no se encontró interpolación de entradas en comandos PowerShell. El script de descubrimiento es constante.
- CSP sin scripts remotos ni eval; capabilities para la ventana local; no permisos genéricos de shell/fs/http expuestos al frontend. React muestra textos recibidos como texto, sin `dangerouslySetInnerHTML` encontrado.
- Actualizador GitHub exige versión estable superior, URL exacta del repositorio, tamaño y digest SHA-256; vuelve a comprobar el hash antes de ejecutar. En MSIX no instala el .exe. El hash desde la misma cuenta no reemplaza una firma independiente.
- Acciones existentes de checkout/setup-node/cache/upload por SHA y credenciales de checkout no persistidas; PRs sin `pull_request_target`.

## Evidencia inicial

- `npm audit --json`: **0 vulnerabilidades conocidas** en ese momento, incluidas dependencias dev. No significa ausencia de fallos desconocidos.
- Búsqueda acotada de patrones de claves privadas, credenciales GitHub y AWS: **1.015 blobs de texto del historial revisados, 12 blobs grandes/binarios omitidos, sin coincidencias**. No es un escáner completo de secretos ni una prueba de inexistencia de credenciales.
- `npm test`: **44 correctas**; `npm run build`: correcto tras correcciones; política local correcta. En Actions del primer commit también pasaron la regresión visual de hover en Edge y el crate `native-tests`. El primer commit pasó 62 + 5 pruebas del crate nativo y 75 del backend (1 ignorada); generó el MSIX experimental. El instalador EXE y el último commit deben terminar de validarse. RustSec se detalla abajo.

## Resultado RustSec y bloqueo de publicación

La primera ejecución de `Security baseline` ([41665557604](https://github.com/marianoarias1/Bimu/actions/runs/41665557604)) revisó ambos lockfiles con cargo-audit 0.22.2. La categoría `vulnerabilities` devolvió 0 en ambos, pero **eso no equivale a auditoría aprobada**: el lock de la aplicación tiene una advertencia `unsound` y una dependencia retirada (`yanked`), que el control exige corregir o evaluar explícitamente. El lock del crate de pruebas no presentó esos avisos. La PR permanece en borrador.

| Hallazgo H-08 / prioridad de tratamiento P1 | Evidencia | Tratamiento pendiente |
|---|---|---|
| Seguridad de memoria | `glib 0.18.5`, [RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html): `VariantStrIter`, corregido desde 0.20.0. | Cargo confirma su ausencia de Windows x64; el árbol Linux llega por GTK/WebKit de Tauri. Exclusión de alcance exacta, con dueño y vencimiento 03/12/2026, en `rust-target-exclusions.json`; el gate revalida la ausencia en cada ejecución. No se declara corregido para Linux. No forzar una versión mayor incompatible mediante edición manual del lock. |
| Paquete retirado | `async-executor 1.14.0` aparece como yanked. El informe no atribuye motivo ni CVE. | Resuelto con `cargo update -p async-executor`: 1.14.1, única dependencia actualizada. Pendiente confirmar la nueva auditoría/CI. Un retiro por sí solo no demuestra explotación. |
| Mantenimiento (P2) | `proc-macro-error 1.0.4` (RUSTSEC-2024-0370); `zbus_names 4.3.5`, `zvariant 5.15.1`, `zvariant_derive 5.15.1` (RUSTSEC-2026-0371/0370/0372). | Ausentes del árbol Windows x64 comprobado con Cargo. Mantener seguimiento de la cadena Linux/upstream; no se presentan como vulnerabilidades explotables por el mero aviso de mantenimiento. |

Se conservan los JSON originales en los artefactos del run. El workflow también genera árboles Cargo separados para Windows y Linux para el análisis de aplicabilidad. No hay ignores globales: la exclusión puntual se comprueba contra `cargo metadata --filter-platform x86_64-pc-windows-msvc`, exige informe completo, cero ignores/filtros del escáner, y falla si cambia su alcance o vence. Cinco pruebas cubren su aplicación, dependencia que entra en Windows, vencimiento, avisos/versiones nuevos, yanked/vulnerabilidades y evidencia inválida. **No mergear ni publicar hasta que el último commit supere CI y la prueba instalada.**

## Deuda abierta / decisiones explícitas

| Prioridad | Tema | Próximo control |
|---|---|---|
| P1 | Firma independiente del EXE y autenticidad ante compromiso de GitHub | Evaluar firma/gestión externa de claves o verificación de firma de actualizaciones. Store firma el MSIX, no convierte al EXE de GitHub en firmado. |
| P1 | Perfil de red: IP privada no equivale a perfil Windows Privado | Listener usa 0.0.0.0 y filtra IP privada/link-local; no se certificó restricción por perfil de red. Recomendar firewall solo en redes confiables; diseñar comprobación del perfil sin romper Ethernet/Wi-Fi/vinculación. No se alteran reglas de firewall automáticamente. |
| P1 | Archivos activos de peer confiado | Un clic en Archivo a mano puede abrir .exe/.lnk/documentos con macros; evaluar advertencia explícita/procedencia para tipos activos. No se eliminó esa función ni se cambió silenciosamente el comportamiento aprobado. |
| P2 | Retención/disco | Descargas recibidas no tienen cuota total/TTL ni borrado seguro al vaciar historial; definir gestión visible que no rompa enlaces/archivos del usuario. |
| P2 | Disponibilidad de red | Deadline limita un intento lento; no impide saturación/reintentos maliciosos de red. Considerar backoff y cuotas por origen con pruebas de reconexión real. Mensajes grandes autenticados aún usan Base64 y pueden superar el tamaño del archivo en RAM. |
| P2 | Privacidad de descubrimiento | Nombre del equipo y tag estable son visibles en la LAN; evaluar anuncios rotatorios/controles sin cambiar protocolo de forma incompatible. |
| P2 | Alertas y auditoría operativa | No hay log de seguridad persistente. Diseñar eventos sin texto/archivos/códigos/claves, con retención limitada y exportación voluntaria. |
| P2 | Pruebas adicionales | Fuzzing de parsers/protocolo, SAST, revisión independiente, chequeo de firma del binario real y pentest LAN en laboratorio controlado. |
